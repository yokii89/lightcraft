# 本地模型自动关键词 · 设计

- 状态：已实现（服务框架已用真实 Python 以 `--stub` 模式端到端验证；真实模型权重的端到端待
  首次下载后执行，步骤见 §14）
- 日期：2026-11-13
- 范围：`lightcraft-extension`（`extension/`），原生代码只允许追加式注册缝
- 模型后端：应用自建的 Python 服务（[`../server/server.py`](../server/server.py)），模型
  [`Qwen/Qwen3-VL-2B-Instruct`](https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct)（Apache-2.0），GPU 使用未量化 BF16；
  **懒启动**（点「启动模型」才拉起）+ **快释放**（5 分钟无调用自动退出，或随时手动停止）
- UI 稿：[`ui-design/auto-keywords.html`](ui-design/auto-keywords.html)

## 1. 目标

用本机运行的视觉大模型，为 LightCraft 图库中的照片自动生成分类和关键字，写入现有的关键字
系统，让用户不必逐张手动打标。

首版必须做到：

- 在扩展面板里点「启动模型」拉起自建服务，选择范围、关键字数量和写入方式，一键开始；
- 模型只在用户本机运行，图片只发往本机回环地址；
- 生成结果按「分类 + 关键字」两级写入，保存为 `父级|分类|关键字` 层级路径；
- 支持预览确认与直接写入两种模式，整批一个撤销步骤；
- 后台运行，有进度、可取消、单张失败不中断整批、可只重试失败项；
- 设置随图库保存，下次打开仍然可用。

## 2. 非目标（v1 明确不做）

- 不在应用进程内跑推理：不引入 candle VLM 实现，不打包模型权重。
  原因见 §4「纯 Rust 约束」。
- 不做云端模型、账号、遥测或上传。
- 不修改 `keywords` 之外的任何照片元数据（不写 rating、label、title、caption）。
- 不做平铺关键字模式；v1 固定两级（分类 + 关键字）。
- 不做自定义分类体系、同义词、中英双语关键字；这些留到后续版本。
- 不做多请求并发；本机模型是瓶颈，v1 串行处理。

## 3. 用户流程

1. 打开左侧「扩展」区块 →「自动关键字」。
2. 点「启动模型」（懒启动）：应用把内嵌的 `server.py` 写到配置目录，找到 Python 解释器并
   拉起服务；服务加载 `Qwen/Qwen3-VL-2B-Instruct`（首次运行自动从 Hugging Face 下载约
   4.0 GiB 权重），状态行显示「启动中…」→「模型就绪 · cuda · 已运行时长」。GPU 固定使用
   BF16，不量化；CPU 调试路径使用 FP32。
   - 依赖缺失或启动失败时，失败卡片显示原因、服务 stderr 尾部和 pip 安装提示；
     应用不会自动改动用户的 Python 环境。
3. 选择范围（选中照片 / 当前视图 / 整个图库）、每张关键字数量、父级关键字、写入方式。
4. 点「生成关键字」。
5. 运行中显示进度、当前文件、失败数、预计剩余时间；可随时停止。
6. 预览模式：逐张展开检查，移除不需要的关键字，取消勾选整张照片；确认后写入。
   直接模式：结束时一次性写入。
7. 写入完成显示数量与用时，可整批撤销；失败照片列出原因并可重试。

### 纯 Rust 约束

- 产品禁止 C/C++ 依赖。模型服务以独立的 Python 进程运行，扩展只发 HTTP 请求，因此产品本身
  仍是纯 Rust；应用内不内嵌 Python 运行时，也不打包模型权重（由 transformers 按需下载）。
- 工作区的 candle 固定在 0.9.2，正是为了避开 `tokenizers` 带进来的 Oniguruma C 库
  （[`Cargo.toml:97`](../../Cargo.toml#L97)）。在进程内实现 VLM 需要自己写视觉编码器、分词器和
  采样，不属于首版范围。
- `lightcraft-fetch` 只有 GET（[`crates/fetch/src/http.rs:555`](../../crates/fetch/src/http.rs#L555)），
  因此 POST 客户端写在扩展内，使用 `std::net::TcpStream`，只支持 `http://`。本机模型服务默认
  都是 HTTP，够用。

## 6. 自建模型服务

### 6.1 生命周期：懒启动、快释放

- **懒启动**：应用不随启动拉起任何模型进程。「启动模型」是唯一入口——`server::start` 把
  `include_str!` 内嵌的 `server.py` 写到 `<配置目录>/extension-server/server.py`（内容相同则
  跳过；无配置目录时退回临时目录并记日志），找到解释器后以
  `python -u server.py --token <token> --model <repo> --idle-timeout 300` 拉起。
- **快释放**：服务空闲看门狗在**无在途请求且距上次调用超过 300 秒**时自行退出（启动后一直
  没被调用同样计时）。「停止模型」按钮随时可手动停止；应用退出后的孤儿进程同样被服务侧
  看门狗兜底退出。请求到达与完成都会刷新计时器，长请求不会被误杀。

### 6.2 启动（Rust 端）

- 解释器：设置的 `pythonPath` 非空则直接使用；否则依次探测 `python`、`python3`、`py` 的
  `--version` 输出（须以 `Python 3` 开头，Windows 商店的存根因此被排除）。成功的解释器在本
  会话内缓存。
- Windows 用 `CREATE_NO_WINDOW` 拉起，不闪控制台窗口。
- stdout 只承载协议行（stderr 是日志、下载进度与 traceback，保留尾部 8 行用于失败显示）：
  - `LISTENING <port>`：HTTP 已绑定 127.0.0.1 随机端口（由系统挑选，避免端口冲突）；
  - `READY <device>`：模型加载完成，可服务（device 为 cuda / cpu / mps / stub）；
  - `LOAD_ERROR <msg>`：加载失败（依赖缺失、下载失败），单行；
  - `IDLE_SHUTDOWN`：看门狗正在退出。
- 管理器状态机 `Stopped → Starting → Ready → (Stopped | Failed)`，每帧 `poll()` 顺带收割
  自行退出的子进程并区分三种结束（空闲自关 / 就绪前退出＝失败 / 就绪后消失）。
- 每次启动生成一个随机 token（时间 + 进程 id + 计数器过 FNV-1a；防的是同机其他进程蹭 GPU，
  不求密码学强度），所有请求必须携带。

### 6.3 生成

`POST http://127.0.0.1:<port>/v1/chat/completions`，头 `Authorization: Bearer <token>`，
OpenAI 形状的消息：

```json
{
  "model": "Qwen/Qwen3-VL-2B-Instruct",
  "messages": [
    { "role": "user", "content": [
      { "type": "text", "text": "<提示词>" },
      { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,<...>" } }
    ] }
  ],
  "temperature": 0,
  "max_tokens": 256,
  "stream": false
}
```

响应：`choices[0].message.content`；`{"error":{"message":…}}` 为失败。模型加载中返回 503。
服务端用 transformers 的 `AutoProcessor` + `AutoModelForMultimodalLM`（模型卡的标准用法），
PIL 解码 base64，`apply_chat_template` 后 `generate(do_sample=False)`；一次 `generate` 由
进程内锁串行化。`--device auto` 依次选 cuda > mps > cpu。

另有 `GET /health`（同 token）返回 `{"status":"loading"|"ready"|"error","device":…}`，供
curl 与未来客户端调试；应用自身的状态以 stdout 协议行为准。

### 6.4 服务端实现要点

- 仅用 Python 标准库（`http.server.ThreadingHTTPServer`）：`--stub` 模式下不需要装任何第三方
  包，集成测试因此可以在没有 torch/权重的机器上跑完整链路。
- `--stub`：不加载模型，`/analyze` 类请求返回固定回复，专供测试。
- SIGTERM 优雅退出；stdout 管道断裂（应用已死）不提前杀服务，交给看门狗。
- **本地权重**：`--model` 也可以是一个权重目录——设置里填绝对路径，或脚本旁存在
  `models/<仓库 id>`（含 `config.json`）时优先离线加载，不再访问 hub。仓库的
  [`server/download_model.py`](../server/download_model.py) 负责把权重下到
  `extension/server/models/`（多连接分段 + 断点续传 + LFS 校验，纯标准库；`models/` 已
  gitignore）。
- **加载与生成性能**：GPU 明确加载 BF16 权重（未量化），`low_cpu_mem_usage` + SDPA 注意力；CUDA 打开 TF32；CPU 回退
  float32（多数 CPU 无原生 bf16 算术）；`READY` 之前用 64×64 灰图跑一次 16 token 的
  预热，把 CUDA 内核编译和缓存分配器的池增长从第一张照片挪进启动阶段（预热失败只记
  日志，不影响就绪）；每次生成向 stderr 记录 token 数与耗时，方便对照页面里的单张超时。
- **视觉塔 patch embed**：Qwen3-VL 的 patch embed 是 kernel == stride == (2,16,16)、单
  个 patch 输入 3×2×16×16 的 Conv3d，每个 patch 实际只是一次点积。cuDNN 9.10 在 1024 px
  照片上选了病态引擎：单次约 45 s、功耗仅 22 W、GPU 利用率约 40%；同一收缩写成 `linear`
  约 2 ms。CUDA 加载后把该模块的 forward 换成
  `F.linear(patch, weight.reshape(O, -1), bias)`（权重不变），视觉塔 42.9 s → 0.11 s，
  25 token 的生成 1.8 s。

### 6.5 HTTP 客户端要求（vlm.rs，不变）

- 只接受 `http://`；`https://` 返回「本机模型服务请使用 http:// 地址」。
- 主机只允许 `127.0.0.1`、`localhost`、`::1`；其他地址直接报错，保证图片不出本机。
- 不跟随重定向、不走代理、不发送服务 token 之外的任何凭证。
- 连接超时 5 s；读取停顿超时可配置（默认 120 s）；总时长上限 180 s。
- 响应上限 4 MiB；错误响应只截取前 2 KiB 显示。
- 支持 `Content-Length`、`Transfer-Encoding: chunked`、连接关闭三种响应体。
- 读取过程中检查取消标志，至少每 200 ms 一次。

## 7. 提示词与结果清洗

### 7.1 提示词（简体中文）

2026-11-13 起生产提示词以 `extension/src/auto_keywords/prompt.txt` 为唯一来源，
Rust 与开发用 Python benchmark 均读取它。现在返回 `category`、`description` 与 `keywords`：
描述 1–3 句、建议 60–120 字，只记可见事实与动作/颜色/空间关系；关键词 1–N 个。
生成预算为 512 tokens，描述清洗到最多 256 字。下方保留的是旧版关键词协议示例。
接受结果后将 AI 描述异步原子写入图库的 `semantic-descriptions.json`，不改用户 caption。
描述绑定照片来源/编辑状态及接受的关键词，撤销关键词或改变照片后旧描述失效。
文本建库使用 GPU 编码，存储与混合检索策略见下节。

### 7.2 描述与向量的存储、检索边界

当前不迁移 SQL。每个图库的 `semantic-descriptions.json` 独立保存已接受描述、照片状态指纹和关键词守护信息，
最多 100,000 条、整文件 64 MiB；用户 caption 保留原样。`semantic-vectors.bin` 是可重建的 512 维 FP32 缓存，
48 字节格式/编码版本头后每条记录 2,088 字节（照片 ID、内容指纹、向量）。两个文件分别原子替换，没有跨文件事务；
描述变化后旧向量因指纹不匹配而停用，更新索引补齐向量。不要因缓存损坏而删除已接受描述。

向量由 BGE-small-zh-v1.5 在硬件 GPU 上按需编码，worker 连续 60 秒无请求便释放模型。词法召回现使用纯 Rust BM25
（`k1=1.2`、`b=0.75`），英文按完整词、中文等非 ASCII 连续文本按双字片段，文件名与有效描述/用户说明、关键词共同参与。
词频、文档频率与平均长度从当前图库快照按查询计算，不额外落盘；BM25 与语义分别取 Top 100，再做 RRF 融合。
模型缺失或向量尚未建立时仍可运行 BM25。先测 1 万/10 万规模的延迟，再决定是否引入 Tantivy 倒排索引；
只有 64 MiB 描述容量或整文件重写成为实测瓶颈时，才评估 redb 等纯 Rust 事务型存储并提供保留原文件的迁移。

```
你是照片图库的自动打标助手。看这张照片，只输出一个 JSON 对象，不要解释：
{"category":"风景","keywords":["雪山","湖泊","日落"]}

要求：
1. category 只能是以下之一：人物、动物、风景、建筑、食物、物体、文档、其他。
2. keywords 为 2 到 {N} 个简体中文词，具体、可检索；不要句子、不要相机参数、不要猜测真实姓名或具体地点。
3. 不要重复 category 或 keywords 中已有的词。
```

- Ollama 用 `format: "json"`；OpenAI 兼容服务靠提示词约束。
- 提示词随每张照片发送，不缓存模型端状态。

### 7.2 解析与清洗

1. 去掉 Markdown 代码围栏；取第一个 `{` 到最后一个 `}`；失败则尝试第一个 `[...]` 数组。
2. 根为对象时读 `category` 与 `keywords`；也接受 `tags` / `labels` 作为关键字数组。
   根为数组时全部当作关键字，分类记为「其他」。
3. 分类不在白名单内时映射别名（`人像`/`people` → 人物、`风光`/`landscape` → 风景、
   `建筑`/`architecture` → 建筑、`美食`/`food` → 食物、`动物`/`animal` → 动物、
   `文档`/`document` → 文档、`物品`/`product` → 物体），仍无法识别则归入「其他」。
4. 每个关键字：
   - 去掉首尾空白和开头的 `#`；
   - `|`、换行、控制字符替换为空格（`|` 是层级分隔符，不能让模型注入层级）；
   - 截断到 32 个字符；
   - 与分类同名、与父级同名、空串丢弃；
   - 忽略大小写去重；
   - 最多保留 N 个（默认 8，范围 1–16）。
5. 清洗后一个关键字都没有 → 该张记为失败「模型没有返回可用的关键字」，不中断整批。

## 8. 关键字写入

- 路径：`{父级}|{分类}|{关键字}`。父级默认 `AI`，可改；留空则写入 `{分类}|{关键字}`。
- 与照片已有关键字按完整路径、忽略大小写去重。
- 整个批次构造一个 `Op::Batch { ops: Vec<Op::SetMeta> }`，通过
  `session.execute_fn("extension.autoKeywords.apply", |s| { s.commit("Auto Keywords", op) })`
  提交：
  - 一个撤销步骤，标签 `Auto Keywords`（在 `zh-hans.json` 译为「自动关键字」）；
  - `execute_fn` 负责 panic 保护、XMP sidecar 自动写和持久化；
  - 提交后调用 `cmd::keywords::note_recent` 把新增关键字加入「最近关键字」。
- 只为至少有一个新关键字的照片构造 `SetMeta`；没有变化就不提交。
- 已知限制：打开「自动写 XMP」时，大图库的写入阶段会同步写 sidecar，可能造成短暂停顿；
  这是与现有批量元数据编辑一致的行为，v1 接受。活动行在写入完成后再消失。

## 9. 状态机

```
Idle ──服务就绪──▶ Ready ──开始──▶ Running ──完成/停止──▶ Review ──写入──▶ Done
  ▲                  │                │                    │
  └──服务停止/退出──┘                └──全部失败──────────┴──▶ Failed
```

- `Ready` 跟随模型服务：服务启动成功进入；服务停止（手动、空闲自关、崩溃）退回 `Idle`，
  服务卡片的状态行与失败卡片说明原因。运行中禁用「停止模型」（请求持续流动，不会触发空闲）。
- `Running`：串行处理；每张结果进入 `results`；取消时停止喂新任务，等当前请求结束。
- `Review`：默认所有照片与关键字选中；用户可移除关键字或取消整张。
- `Applying`：构造并提交批次；活动行此时仍在。
- `Done`：显示写入数量、关键字数、用时、失败列表；可直接重试失败项。
- `Failed`：无任何可用结果时显示失败汇总，保留设置。

范围枚举：

- 选中照片：`Session::selected()`；
- 当前视图：`Session::visible()` 的顺序；
- 整个图库：`catalog.photos()` 中 `in_library()` 的照片，按目录顺序。

所有范围都跳过视频（`Photo::is_video()`）。启用「跳过已有关键字的照片」时，跳过
`meta.keywords` 非空的照片，并在进度里计入「跳过」。

## 10. UI 规格

详见 [`ui-design/auto-keywords.html`](ui-design/auto-keywords.html)（可直接浏览器打开，
可切换状态与面板宽度）。

- 停靠：原生 `Panel::Extension`，默认宽 320 px，最小 200，最大 720。
- 五个可切换状态：就绪、运行中、待确认、已完成、服务失败。
- 就绪页分区：模型服务、范围、关键字、写入方式、主按钮。
- 模型服务卡片：状态行（未启动 / 启动中… / 模型就绪 · 设备 · 已运行时长）+「启动模型 /
  停止模型」开关；空闲自关与手动停止在状态行下有一行说明；模型仓库、Python 解释器
  （留空自动探测）、单张超时三个字段；懒启动/快释放与隐私两行说明。
- 服务失败卡片：原因、服务 stderr 尾部、「再试一次」、pip 安装提示、隐私说明。
- 运行中：进度条、`已完成 / 总数`、当前文件、失败数、预计剩余时间、停止按钮、
  最近完成的两张（可展开）。
- 待确认：汇总计数、全部接受/全部丢弃、逐张展开的关键字 chips（× 移除）、整张勾选、
  底部固定「写入 N 张照片」。
- 已完成：写入数量、关键字数、用时、失败列表与重试、撤销整批。

所有文案走 `i18n::tr`；英文源文案与简体中文对照见 HTML 稿末尾的「文案审计表」。

## 11. 隐私与安全

- 只连接回环地址，图片不出本机；非回环地址在检测阶段直接拒绝。
- 不保存图片副本到磁盘；编码后的 JPEG 只存在于内存和请求体。
- 错误信息不回显图片内容；模型返回的文本按不可信输入清洗。
- 响应体、关键字数量、关键字长度、请求时长都有上限；读取检查取消标志。
- 设置文件读取按不可信 JSON 处理：大小上限 64 KiB、serde 默认值、解析失败回退默认设置。

## 12. 性能

- 送图长边 1024 px（`render_job`，不裁剪），JPEG 质量 85，单张通常 100–400 KiB。
- 渲染在 worker 线程；UI 线程只构造 `RenderJob`（只读目录元数据）和应用结果。
- 串行请求；ETA 用最近 10 张的平均耗时估算。
- 渲染耗时取决于原片（raw 解码约 0.2–1.5 s）；模型耗时取决于本机硬件和模型大小。
- 不在扩展页里显示缩略图网格；预览用文件名 + 关键字 chips，避免额外渲染负担。

## 13. 设置持久化

文件：`<图库目录>/auto-keywords.json`（没有打开图库时仅保存在内存）。

```json
{
  "version": 2,
  "modelRepo": "Qwen/Qwen3-VL-2B-Instruct",
  "pythonPath": "",
  "maxKeywords": 8,
  "parent": "AI",
  "skipTagged": false,
  "applyMode": "Review",
  "timeoutSecs": 120
}
```

- `pythonPath` 留空时按 `python` / `python3` / `py` 自动探测。
- v1 文件（endpoint/protocol 指向已移除的 Ollama 后端）读入时其未知字段被忽略，其余字段照常
  生效，模型与解释器取默认值。
- 用 `lightcraft_catalog::safe_file::write_atomic` 原子写入；失败只提示，不阻断生成。
- 在开始生成或启动服务时保存一次；控件修改后延迟 500 ms 再保存。

## 14. 测试

### 单元测试（`extension/`）

- HTTP 客户端：本地 `TcpListener` mock
  - POST `/v1/chat/completions` 请求体字段与 `Authorization: Bearer` 头；
  - `Content-Length`、chunked、连接关闭三种响应；
  - 超大响应被拒绝；连接被拒、停顿超时、取消标志；401（token 错）；
  - 非回环地址、`https://`、缺端口被拒绝。
- 服务管理器（`server/tests.rs`）
  - 协议行解析：`LISTENING`/`READY`/`LOAD_ERROR`/`IDLE_SHUTDOWN`、坏行被拒不崩溃；
  - 收割的三种结束：空闲自关、就绪前退出、就绪后消失；
  - token 每次启动不同；
  - **真实 Python 端到端（`--stub`，无 Python 时按 skip 记录）**：spawn → 监听 → analyze →
    错误 token 401 → `--idle-timeout 2` 自动退出；管理器 `start` → Ready → `stop`。
- 解析：代码围栏、前后夹杂解释、数组根、分类别名、未知分类、重复关键字、
  超长关键字、`|` 注入、空结果。
- 路径与去重：父级为空、已有关键字大小写不同、同批重复。
- 应用：用 `Session::with_demo()` 构造结果，提交一个批次后断言关键字写入、
  再撤销断言恢复原状、且撤销历史只增加一步。
- 设置：序列化往返、损坏 JSON 回退默认值、v1 文件（Ollama 字段）兼容读取、
  空模型仓库回退默认模型。
- 页面：headless 渲染；服务卡片在停止/就绪两种状态下恰好显示开关的一半。

### 手工端到端（真实模型）

1. `pip install -r extension/server/requirements.txt`（NVIDIA 显卡先按 pytorch.org 装 CUDA 版
   torch）。
2. 用 CC0 样片（`cargo xtask corpus --download`，不入库）导入一个临时图库。
3. 扩展面板 → 自动关键字 →「启动模型」：首次自动下载约 4.0 GiB 权重，状态行变为
   「模型就绪 · cuda」。网络慢时改用 `python extension/server/download_model.py` 先把权重
   下到 `extension/server/models/`（见 §6.4），再把「模型仓库」填成本地路径。
4. 选 5 张 → 预览 → 移除一个关键字 → 写入；检查关键字树出现 `AI|风景|…`，XMP sidecar
   同步，撤销一次回退整批。
5. 空置 5 分钟确认「空闲已自动关闭」；点「启动模型」可再次拉起；运行中取消、停掉 Python
   进程的失败提示、重试失败项。

## 15. 验收标准

- 在装好 Python 依赖与 `Qwen/Qwen3-VL-2B-Instruct` 权重的机器上，5 张样片能生成简体中文分类与
  关键字；
- 关键字以 `父级|分类|关键字` 写入，重复关键字不重复添加；
- 预览模式可移除关键字/整张照片，直接模式跳过预览；
- 整批恰好一个撤销步骤，撤销后照片恢复原有关键字；
- 运行中活动栈有行、可取消；关闭扩展面板不中断；
- 单张失败不中断整批，可只重试失败项；
- `cargo fmt --all -- --check`、`cargo test -p lightcraft-extension`、
  `cargo clippy -p lightcraft-extension --all-targets -- -D warnings` 通过；
- 除 `crates/ui-egui/locales/zh-hans.json` 的数据条目外，没有原生文件改动。
